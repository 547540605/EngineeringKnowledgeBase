# Modbus RTU 主从通信与报文结构

## 所属领域

```text
Computer Science
└─ Networking
   └─ Industrial Protocols
      └─ Modbus
         └─ RTU
```

Modbus RTU 规定主站和从站如何把设备地址、操作类型、寄存器地址、数据和校验信息组织成字节报文。它通常通过 RS485 线路传输，但 Modbus RTU 和 RS485 不是同一个概念。

## 主站请求、从站响应

Modbus RTU 的常规通信流程是：

```text
主站发送请求
    ↓
指定地址的从站处理请求
    ↓
从站返回正常响应或异常响应
```

在物料台项目中：

```text
MaterialTable 服务：Modbus 主站
EPG-HP 电动夹爪： Modbus 从站
```

从站通常不会主动发送业务报文，而是等待主站请求。

## RTU 请求报文的基本组成

常见请求可以抽象为：

```text
┌──────────┬────────┬────────────┬──────────┐
│ 从站地址 │ 功能码 │ 请求的数据 │ CRC 校验 │
└──────────┴────────┴────────────┴──────────┘
   1 byte    1 byte      N byte      2 byte
```

“请求的数据”随功能码变化。例如读取寄存器时包含起始地址和读取数量，写寄存器时包含寄存器地址和待写数据。

## 完整读取请求示例

假设：

```text
从站地址：    0x09
功能码：      0x03（读取保持寄存器）
起始地址：    0x03E8
读取数量：    0x0001（读取 1 个寄存器）
```

完整请求为：

```text
09 03 03 E8 00 01 05 32
```

逐段拆解：

| 字节 | 含义 |
| --- | --- |
| `09` | 请求发送给从站地址 `0x09` |
| `03` | 功能码 `0x03`，读取保持寄存器 |
| `03 E8` | 起始寄存器地址 `0x03E8`，高字节在前 |
| `00 01` | 读取 1 个寄存器，高字节在前 |
| `05 32` | CRC，在线路中低字节 `05` 先发送 |

CRC 的计算输入是前面的字节：

```text
09 03 03 E8 00 01
```

计算得到的 16 位 CRC 数值为 `0x3205`，放进 Modbus RTU 报文时按照低字节在前排列为 `05 32`。

## 从站地址

从站地址用于区分同一总线上的不同设备。主站发出的请求会出现在总线上，但只有地址匹配的从站应当处理并响应。

说明书示例中的 `0x09` 只是示例地址。实际开发必须读取或确认设备当前配置地址，不能仅根据示例硬编码。

## 功能码

功能码告诉从站“这次要执行什么操作”。EPG-HP 说明书中涉及的常见功能码包括：

| 功能码 | 含义 |
| --- | --- |
| `0x03` | 读取保持寄存器 |
| `0x04` | 读取输入寄存器 |
| `0x06` | 写单个保持寄存器 |
| `0x10` | 写多个保持寄存器 |

同一个寄存器地址配合不同功能码，不一定都是合法操作。必须按照设备说明书指定的寄存器类型和读写权限使用。

## 寄存器地址和读取数量

请求中的：

```text
03 E8
```

表示起始地址 `0x03E8`，不是寄存器数据。

请求中的：

```text
00 01
```

表示读取 1 个寄存器。一个 Modbus 寄存器通常为 16 bit，所以正常响应会返回 2 个数据字节。

## 正常响应示例

假设 `0x03E8` 寄存器当前数据为 `0x0001`，从站可以返回：

```text
09 03 02 00 01 98 45
```

逐段拆解：

| 字节 | 含义 |
| --- | --- |
| `09` | 响应来自从站 `0x09` |
| `03` | 对功能码 `0x03` 的正常响应 |
| `02` | 后面包含 2 个数据字节 |
| `00 01` | 一个寄存器的数据 `0x0001` |
| `98 45` | CRC 低字节和高字节 |

请求中填写的是“读取几个寄存器”，响应中填写的是“后续有几个数据字节”，两者单位不同：

```text
请求数量 1 个寄存器
响应字节数 2 个字节
```

可以把一个寄存器理解为一个固定容量为 2 byte 的盒子：

```text
1 个寄存器 = 2 byte
2 个寄存器 = 4 byte
3 个寄存器 = 6 byte
```

因此请求读取 3 个寄存器时，请求数量写 `00 03`；正常响应中的字节数写 `06`，后面再跟 6 个数据字节：

```text
请求：09 03 03 E8 00 03 ...
                      └─ 读取 3 个寄存器

响应：09 03 06 [数据1][数据2][数据3] ...
          └─ 后面共 6 个数据字节
```

请求和响应描述的是同一批数据，只是计量单位不同：请求按“寄存器个数”计数，响应按“实际数据字节数”计数。

## CRC 的职责

CRC 用于检查从站地址、功能码和数据等报文内容在传输过程中是否发生错误。

接收方会对收到的正文重新计算 CRC：

```text
计算结果与报文 CRC 相同 → 报文可能完整，继续解析
计算结果不同             → 丢弃报文或报告通信错误
```

CRC 正确只说明接收方收到的正文与报文中携带的 CRC 相符，报文在传输途中大概率没有损坏。它不自动证明 Modbus 格式、设备地址、寄存器地址或业务命令正确。

例如主站使用了一个不存在的寄存器地址，但仍然可以针对这条错误请求计算出完全正确的 CRC。从站通过 CRC 检查后，还会继续检查功能码、地址和数据是否合法，并可能返回异常响应。

```text
串口帧检查通过 ≠ CRC 一定正确
CRC 检查通过     ≠ Modbus 字段一定合法
Modbus 字段合法   ≠ 业务意图一定正确
```

## 异常响应

从站收到格式正确但无法执行的请求时，可能返回 Modbus 异常响应。异常响应通常把原功能码的最高位置为 1：

```text
原功能码：0x03
异常功能码：0x83
```

后面再携带异常码，用于说明非法功能、非法地址或非法数据等原因。异常响应不是串口乱码，也不等同于超时；它说明从站成功收到并理解了报文框架，但拒绝了具体请求。

## 报文边界

Modbus RTU 没有固定的“开始字符”和“结束字符”，主要使用线路上的静默时间区分报文。发送方应连续发送一帧，帧与帧之间保留规定的静默间隔。

实际开发优先使用成熟的 Modbus 库处理帧间隔、CRC、超时和收发方向，不应在没有必要时手写整个协议栈。

1. Modbus RTU 使用主站请求、从站响应的流程。
2. 报文至少包含从站地址、功能码、业务数据和 CRC。
3. `03 E8` 可以表示寄存器地址 `0x03E8`。
4. 功能码 `0x03` 表示读取保持寄存器。
5. 请求中的寄存器数量与响应中的数据字节数单位不同。
6. CRC 数值在 RTU 报文中按低字节在前发送。
