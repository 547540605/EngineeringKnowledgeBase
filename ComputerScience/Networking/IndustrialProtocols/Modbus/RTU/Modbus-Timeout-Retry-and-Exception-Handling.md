# Modbus 超时、重试与异常响应

## 所属领域

```text
Computer Science
└─ Networking
   └─ Industrial Protocols
      └─ Modbus
         └─ RTU
            └─ Reliability and Error Handling
```

一次 Modbus 请求不只有成功和失败两种简单结果。主站需要区分正常响应、协议异常响应、通信超时、报文损坏和设备动作失败，因为它们的原因和处理方式不同。

## 一次请求的常见结果

```text
主站发送请求
    ├─ 收到正常响应
    ├─ 收到 Modbus 异常响应
    ├─ 收到 CRC 错误或格式不完整的响应
    └─ 在规定时间内没有收到响应
```

### 正常响应

从站接受请求，并返回对应功能码的正常响应。

对于写操作，正常响应通常只说明寄存器写入请求被接受，不代表机械动作已经完成。

### Modbus 异常响应

从站成功接收并识别了报文，但认为请求无法执行。异常响应会把原功能码最高位置为 1：

```text
原功能码 0x03 → 异常功能码 0x83
原功能码 0x06 → 异常功能码 0x86
原功能码 0x10 → 异常功能码 0x90
```

后面通常跟一个异常码：

| 异常码 | 常见名称 | 基本含义 |
| --- | --- | --- |
| `0x01` | Illegal Function | 从站不支持该功能码 |
| `0x02` | Illegal Data Address | 寄存器地址或地址范围无效 |
| `0x03` | Illegal Data Value | 数量、参数或数据格式不合法 |
| `0x04` | Server Device Failure | 从站处理请求时发生内部故障 |

异常响应说明线路、串口参数和请求框架大概率已经工作，问题更靠近功能码、地址、参数或设备内部状态。

### CRC 错误或报文不完整

接收方得到了一些字节，但校验失败、长度不符合预期或帧边界错误。可能原因包括干扰、A/B 接线问题、串口参数不一致、接收缓冲处理错误或超时设置过短。

这类报文不能继续当作有效业务响应解析。

### 通信超时

主站发送请求后，在本地设定的等待时间内没有获得有效响应。超时是主站的等待结果，不是从站返回的一种 Modbus 异常码。

可能原因包括：

```text
从站地址错误
设备未供电或未连接
A/B 接反
串口参数不一致
从站正在故障或无响应
USB 转 RS485 方向切换问题
响应到达但被 CRC 或长度检查丢弃
超时时间设置过短
```

## 通信超时与动作超时

这两个超时必须分开：

```text
通信超时：发送请求后，多久没有收到有效 Modbus 响应
动作超时：夹爪接受命令后，多久仍未完成机械动作
```

例如：

```text
写命令在 50 ms 内收到响应 → 通信成功
夹爪 3 s 后仍未到达目标位置 → 动作超时
```

动作执行期间可以不断成功读取状态寄存器，因此“通信正常”和“动作失败”完全可以同时发生。

## 为什么不能无脑重试写操作

请求超时并不等于从站没有执行请求。可能发生：

```text
主站发送写请求
    ↓
从站收到并执行写入
    ↓
从站响应在途中丢失
    ↓
主站只看到超时
```

此时主站无法仅凭超时判断：

```text
请求根本没到从站
还是请求已执行、只有响应丢了
```

这称为结果不确定。若命令是触发一次动作、计数加一或切换状态，直接重发可能导致重复执行。

## 读操作与写操作的重试差异

### 读操作

读取通常不改变设备状态，因此有限次数重试一般比较安全：

```text
读取超时
→ 等待短暂间隔
→ 重试有限次数
→ 仍失败则报告通信故障
```

### 写操作

写操作要根据语义处理：

```text
重复写相同目标值：通常更接近幂等，但仍要遵循设备说明书
触发型命令：重复写可能再次触发动作
```

较稳妥的策略是：

1. 写响应超时后，不立即认定未执行。
2. 若设备提供足够的当前状态、目标值或结果反馈，可以读取并尝试判断命令是否已生效。
3. 只有反馈能够明确证明命令未应用，并且设备允许时，才重试写入。
4. 设置有限重试次数和总超时时间。

## 状态寄存器能确认到什么程度

状态寄存器通常保存设备当前状态，而不是完整历史记录。设备即使暂时无法把响应送回主站，也可能继续执行已经收到的命令，并在内部持续更新当前位置、动作状态、工件检测和故障等反馈。

通信恢复后，主站可以读取这些当前反馈并与原命令的预期结果比较：

```text
原命令要求移动到位置 100
当前位置反馈已经是 100
动作完成标志已经置位
没有故障
```

这些信息可以支持“该目标大概率已经生效”的判断。

但状态寄存器不一定能证明某一条历史命令执行过，也不能天然确认执行次数。例如：

```text
夹爪执行命令后又被其他命令改回原状态
同一目标命令被重复执行
设备只反馈当前位置，不反馈最后目标值或完成标志
设备断电重启后状态丢失
```

此时读取当前状态仍无法消除不确定性。只有设备协议提供命令序号、最后执行结果、事件历史或足够明确的目标回显时，才能更可靠地关联到具体命令。Modbus RTU 通用协议本身不提供业务命令序号，这类能力必须由具体设备寄存器协议额外设计。

因此，“写超时后读取状态”是一种依赖设备反馈能力的补救策略，不是对所有 Modbus 设备都成立的保证。

## 幂等的含义

同一个操作执行一次或重复执行多次，最终状态相同，称为幂等。

```text
把目标速度设置为 100：通常是幂等操作
让计数器加 1：不是幂等操作
触发一次夹取：是否幂等取决于设备命令语义
```

不能只因为使用的是“写寄存器”，就假设重复发送一定安全。

## 并发访问串口

一条两线 RS485 总线在某个时刻通常只应有一个未完成的主站请求。若多个线程同时向同一个串口写入，请求字节可能交叉，响应也难以与请求匹配。

常见做法是对同一串口或同一 Modbus 主站实例进行串行化访问：

```text
请求 A 发送并等待响应
        ↓
请求 A 完成
        ↓
请求 B 才能发送
```

在 .NET 中可以使用锁、`SemaphoreSlim` 或由 Modbus 库提供的线程安全机制。具体选择取决于同步或异步调用方式。

## 日志应记录什么

排查工业通信时，至少记录：

```text
时间
串口与串口参数
从站地址
功能码
寄存器地址与数量
发送报文十六进制
接收报文十六进制
耗时
重试次数
CRC、超时或异常码
```

日志中的控制参数和设备标识是否需要脱敏，应根据项目要求确定。

## EPG-HP 的通信中断提示

EPG-HP 说明书提到，连续约 1 秒没有数据通信时可能显示通信中断状态，并建议在需要维持通信监测时让主站以高于 1 Hz 的频率发送请求。

这属于设备自身的通信监测逻辑，与主站单次请求的响应超时时间不是同一个概念。是否需要周期轮询以及通信中断是否影响动作，应根据实际设备行为和项目要求验证。

## 当前阶段应掌握

1. Modbus 异常响应与通信超时不是同一件事。
2. CRC 错误报文不能继续作为有效响应解析。
3. 通信超时与夹爪动作超时必须分开。
4. 写请求超时可能处于“已执行但响应丢失”的不确定状态。
5. 读操作通常可以有限重试，写操作要根据幂等性和状态反馈决定。
6. 同一串口上的请求应串行执行，避免报文和响应混乱。
