## Problem

设备 WebAPI 常见两种相反问题：

1. 把 HTTP、状态机、硬件调用和配置全部写进 Controller，难测试且无法替换硬件。
2. 为每个请求模型、接口、枚举、薄包装类分别建文件；小设备服务会出现大量只有几行代码的文件，调用链难追踪，维护成本高于隔离收益。

文件数量不是架构质量指标。拆分应服务于独立变化、独立替换或独立测试，而不是机械套用分层目录。

## Durable Rules

### 1. 先按变化边界拆，再按类型名拆

同一设备能力中会一起变化的请求、响应、状态枚举可以放入同一 Contracts 文件；不要因为每个 record 都有名字，就各自建一个文件。

应拆开的是独立变化的能力，例如：

- 不同硬件驱动或协议适配；
- 独立状态机；
- 独立后台任务；
- 可单独替换的存储或算法；
- 规模足以妨碍阅读的业务模块。

### 2. Controller 只处理 HTTP 边界

Controller 负责路由、参数绑定、调用来源、HTTP 状态和统一返回外壳；不直接调用硬件库，不保存设备状态，不编排多步硬件动作。

### 3. 只在存在替换点时抽象硬件接口

真实硬件和模拟硬件、两种厂商协议、或未来明确会替换的设备，应通过一个硬件接口隔离，并由 DI 按部署配置注册。

没有第二种实现、也没有独立替换需求的纯业务薄包装，不应为了“所有服务都有接口”而新增 `I...Service` 文件。

### 4. 模拟模式必须不依赖真实硬件初始化

如果配置选择模拟实现，启动路径不能预先枚举真实机器人、相机或 IO，再注册 Mock。否则模拟模式在没有现场硬件时仍会启动失败，失去本地开发和接口联调价值。

### 5. 硬件读取失败不能伪装成业务状态

读取在位 IO 失败时，不能把错误吞掉并返回 `occupied = false`。调用方会把“传感器/通信故障”误判为“工位空闲”。应返回设备未就绪或驱动通信错误，并在日志保留原始异常。

### 6. 固定设备配置不要套用动态标定模型

工位数、类型和 IO 映射固定时，使用明确的静态配置。只有现场确实通过标定决定行列、间距、坐标或通道映射时，才引入动态生成槽位、标定会话和轨迹配置。

### 7. 业务调度与本机设备能力分离

锁、心跳、任务队列、AGV/机器人编排仅在本服务真正拥有跨设备业务责任时才实现。若客户平台负责调度，设备服务只提供本机状态与动作，不保存客户物料业务、任务生命周期或机器人坐标。

### 8. 每个小型设备服务的最小合理结构

适用于单一设备、少量接口、单一硬件适配边界的 ASP.NET Core 服务：

```text
Program.cs                     启动、DI、HTTP 管道
Models/Contracts.cs            同一设备的请求、响应、错误与状态
Services/<Device>Runtime.cs    状态机、互斥、业务动作、硬件接口与模拟实现
Controllers/<Device>Api.cs     HTTP 路由和统一响应
Infrastructure/Logging/...     跨设备可复用的日志设施
```

当某一模块的代码量、状态复杂度或替换需求增长时，再从 Runtime 中拆出独立文件；不要预先按每个类拆文件。

## Review Checklist

1. 这个文件或接口是否有独立变化或替换原因？没有则与同一能力合并。
2. Controller 是否只做 HTTP 边界工作？不是则下沉到服务层。
3. Mock 模式是否无需任何真实硬件即可启动？
4. 传感器、驱动和超时失败是否与“正常业务状态”可区分？
5. 当前设备究竟负责本机动作，还是确实负责客户业务调度？
6. 固定配置是否被错误设计成动态标定和任务系统？

## Example

对于固定 17 个工位、一个折叠机和在位 IO 的缓存台：

- 工位查询、折叠请求和统一返回可放在同一 Contracts 文件；
- 运行模式、动作互斥、真实/模拟 IO 和折叠机适配可放在同一 Runtime 文件；
- 把“工位 1 的请求模型”“工位 2 的请求模型”或每个小接口各自拆文件没有收益；
- 物料 ID、AGV 锁、机器人轨迹、动态二维码/坐标标定不属于该设备服务，除非需求明确把这些责任交给它。

## Notes

这些规则约束的是小型独立设备服务。复杂领域、多团队并行开发、多个可发布模块或协议适配显著增长时，应重新评估拆分粒度。
